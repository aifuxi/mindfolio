# Mindfolio 技术实施规格

Status: ready-for-agent

说明：核心技术方向和两阶段功能范围已确认。本文将已确认选择与工程默认约定合并为实施依据；验收方案按工程默认值纳入，测试侧重点可根据管理者反馈调整，实际部署信息和兼容性验证在对应阶段补齐。

## 问题陈述

管理者需要先交付一个可靠的个人管理系统，用于项目任务、习惯、每日记录和每周回顾，再扩展公开网站。旧博客方案只是参考，本项目从零建设，没有历史业务数据需要迁移；需要一套适合唯一管理者、自有小型 VPS 和自有 Vue 组件库的技术方案，避免前后端契约重复维护，并明确发布、数据保留和故障恢复边界。

## 解决方案

采用 Rust 模块化单体与 PostgreSQL，管理端使用 Vue 3、TypeScript、Vite 和自有 Semi UI Vue 组件库。Rust DTO 生成 OpenAPI，再生成前端类型；前后端在同一仓库协作，分别构建和部署。第一阶段完成私人管理、登录、导出、发布与备份；第二阶段加入 Nuxt SSR 公开网站及 OSS 文件访问。

在 Ubuntu 服务器上使用 Docker、Caddy 和 Portainer，镜像由 GitHub Actions 构建并保存到 GHCR，管理者手动选择版本部署。公开内容和图片按当前发布状态响应；服务器故障恢复目标为最多丢失 1 小时数据、24 小时内恢复使用，历史备份保留 30 天。

### 工程默认约定

以下属于本规格给出的工程默认值，精确依赖版本在最小工程验证后锁定；不将文档兼容性核对视为已通过项目运行验证。

| 项目 | 默认方案 |

| 契约生成 | utoipa 导出 OpenAPI 3.1.0，openapi-typescript 生成 TypeScript 类型 |

### mise 环境与统一质量检查

mise 是项目环境与命令的统一入口。Rust、Node.js、pnpm 和 mise 自身固定经过兼容验证的精确版本；提交工具配置与锁文件，CI 和构建环境按锁定结果安装，不使用浮动的 latest。Rust 通过 mise 的 Rust 后端安装 rustfmt 与 Clippy 组件；Cargo 和 pnpm 仍分别管理依赖并提交锁文件，ESLint 与 Prettier 作为前端开发依赖固定版本。Rust 版本只维护一份权威配置，其他必须声明的版本由该配置派生或校验一致性。

项目命令行操作使用 mise 任务；临时命令使用 `mise exec -- <命令>`，任务内部再调用底层工具。首次安装 mise 本身属于环境引导。Docker 继续承载 PostgreSQL、Caddy、Portainer 和应用服务，服务镜像独立固定版本；服务器部署、迁移、备份、恢复及诊断的命令行操作在对应功能建立时封装为 mise 任务，Portainer 面板仍用于已确认的人工版本发布。生产环境只准备实际运行和运维所需工具，应用启动不临时下载依赖或安装开发工具链。

| 统一入口 | 行为 |
|---|---|
| `mise run setup` | 按锁文件准备当前阶段的工程依赖及必要生成步骤 |
| `mise run dev` | 启动当前阶段的本地开发服务 |
| `mise run fmt` | 用 rustfmt 和 Prettier 修复格式 |
| `mise run fmt:check` | 检查格式，不修改源文件 |
| `mise run lint` | 执行 Clippy 与 ESLint，警告也使任务失败，不自动修复 |
| `mise run typecheck` | 检查前端 TypeScript 和 Vue 单文件组件类型，第二阶段纳入 Nuxt |
| `mise run check` | 汇总格式、lint 与类型检查 |
| `mise run test` | 运行当前阶段已经建立的测试 |
| `mise run build` | 构建当前阶段应用产物 |
| `mise run ci` | 组合检查、契约一致性、测试和构建，任一失败则整体失败 |

Rust 使用稳定工具链支持的 rustfmt 配置与 Clippy 规则，检查工作区全部目标；是否启用所有 feature 取决于实际组合是否兼容。前端采用 ESLint flat config，配置 Vue 与 TypeScript 规则，区分浏览器代码和 Node.js 配置文件的环境。Prettier 负责格式，ESLint 负责代码质量，兼容配置放在最后关闭冲突规则，不将 Prettier 重复接入 ESLint 运行。Vite 管理端单独执行 Vue 类型检查，不能以构建成功替代类型检查；第二阶段 Nuxt 接入自身生成的 ESLint 配置并复用公共约定。

命令与 CI 在真实最小工程建立后验收。检查不修改源文件，任务正确表达生成步骤与检查之间的依赖；未建立的第二阶段应用不提前注册空任务，也不能以跳过检查获得成功状态。工具缺失、版本不符或底层检查失败必须明确报错。具体配置和验证范围见首个工程基础任务。

### 应用和模块边界

后端按账号与会话、项目任务、任务完成记录、习惯与打卡、每日记录、回顾与导出组织业务模块。公开文章、网站配置、友链、媒体访问在第二阶段加入；模块内部封装 SQLx 查询及事务，HTTP 层使用独立请求与响应 DTO。

两个前端共享生成的接口类型、HTTP 基础封装和合适的纯工具；路由、页面状态及 SSR 请求上下文分别维护。组件库使用公开入口，并在接入时验证实际发布版本、Vue 版本和样式行为；公开端仅验证所需组件的 SSR 与 hydration，避免把管理端的浏览器状态带入服务端共享状态。

业务实体表、Session、每日记录、习惯打卡和任务完成记录均通过版本化数据库迁移建立。迁移包含主外键、唯一性和必要索引；每日记录按日期唯一，习惯打卡按习惯和日期唯一，子任务深度及项目归属由事务内校验约束。没有旧业务数据迁移任务，但需要从空库建立结构并支持后续升级。

### 契约与接口约定

Rust DTO 是接口契约来源，生成的 OpenAPI 固定为 3.1.0；不因库升级自动切换协议版本。CI 校验文档、重新生成类型、检查产物差异并执行前端类型检查。数据库模型与对外 DTO 分开，敏感字段不进入响应模型；生成的静态类型不能替代 Rust 的运行时输入验证。

所有资源 ID，包括嵌套引用、请求参数和关联对象，都使用字符串，前端将其视为不透明标识。日期字段不经过 JavaScript Date 或 UTC 时间戳中转；实际事件时间再按业务时区归属到相应日期。缺省字段、显式清空及枚举值在 DTO 中表达一致。

错误响应统一包含稳定业务错误码、中文可读消息与请求标识，字段验证错误按字段表达。常规列表具备有上限的分页、稳定排序和筛选；初始采用页码分页并以 ID 作为同序条件，避免返回无界集合。

更新与删除携带实体预期版本，数据库在一次原子写入中校验版本并递增；多实体约束在同一事务中处理。版本冲突返回 409，资源不存在或已删除返回 404。客户端保留当前输入并显示冲突，不自动覆盖服务器的新版本；传输重试不能生成重复的完成事实或打卡记录。

### 登录与私人数据

首次管理者创建和密码重置通过服务器命令完成。密码使用 Argon2id 哈希，计算放在合适的阻塞执行环境并限制并发；参数、登录限流和 Session 的空闲及绝对有效期作为配置，在目标机器上验证。

Session 存储在 PostgreSQL，登录成功轮换会话标识，退出撤销当前会话，改密或重置撤销全部会话。Cookie 设置 Secure、HttpOnly 和 SameSite，限定管理子域而不设置跨子域 Domain。管理端以同源方式请求 API；Rust 对每个管理请求鉴权，写请求校验 CSRF token 和请求来源，不能仅依赖 SameSite 或前端隐藏页面。

项目、任务、习惯、每日记录、回顾和导出均为私人内容。公开 API 在 Rust 内部直接筛选可公开数据，Nuxt 不使用管理接口取得完整数据后再隐藏。

### Markdown 与完成历史

任务说明及每日记录保存 Markdown 原文，编辑和预览使用同一套解析约定。原始 HTML 不执行，链接仅接受经过解析和协议校验的地址；新窗口链接隔离 opener。第一阶段关闭图片语法的远程加载，避免文本预览隐式扩展为附件或远程资源功能。文章编辑体验在第二阶段实现前选择，不从本决定推导富文本编辑器。

任务或子任务从非完成状态进入“已完成”时，在同一事务中更新状态并追加任务完成记录。重复提交完成请求不产生重复记录；重新打开只改变当前状态，之后再次完成可产生新的完成事实。父任务依旧手动完成，有未完成子任务时按功能规格提示。

任务完成记录只保存回顾所需的任务标识、完成时间及任务标题、所属项目名称快照。删除任务或项目会使相关内容从当前列表和详情中退出，但不级联删除已有完成记录；已删除任务的历史不提供可操作的任务详情入口。每日汇总与每周回顾按完成时间读取历史，而非按任务当前状态倒推；展示区间内默认按任务聚合并使用区间内最近一次完成快照，导出保留全部完成事实。

当前编辑不回写历史名称快照。字段修改、项目移动、归档、取消等不自动创建完成记录；此机制服务既有回顾和导出，不扩展全量操作审计、回收站或历史编辑入口。

### 日期与习惯计算

服务端按 Asia/Shanghai 计算“今日”和日期区间，前后端遵守相同约定；默认周一为每周起点。任务计划和截止日期不携带时分，任务完成记录使用实际完成时间；每日记录与打卡使用所归属的业务日期。

习惯按每日或每周灵活指定天数执行，打卡以日期和完成状态记录；补记作用于所选日期，暂停期间排除在目标统计之外。习惯模块实现时用跨周、跨月、暂停覆盖整周及部分周等示例固定分母、目标天数和空统计区间的展示规则，保持已确认的功能含义；这些边界在对应模块验收中覆盖。

### 公开网站与媒体访问

第二阶段由 Nuxt SSR 请求 Rust 公开 API，输出正文及网站配置的搜索、分享元信息。发布、修改或撤回事务成功后发起的新公开读取反映最新状态；草稿及撤回文章不出现在列表中，公开详情返回 404 且不输出正文。已经打开的页面刷新后取新内容，搜索引擎索引更新时间不属于应用控制范围。

首版可变公开内容的 HTML、API 及对应 404 使用 no-store，不启用这些路由的预渲染、SWR、ISR 或跨请求内容缓存。带内容哈希的构建资源可独立缓存；浏览器后续导航也重新请求文章状态。公开统计只在公开页面按已配置的 GA4 或百度统计开关加载。

文件元信息与对象标识保存在 PostgreSQL，文件内容进入 OSS。Rust 优先验证 aws-sdk-s3 的适配情况，按实际区域验证 Endpoint、virtual-hosted 寻址、签名、传输编码、预签名、查询和删除；不能从 S3 兼容声明推导出所有默认行为都可用。

上传采用后端鉴权后签发指定临时对象的短时授权，浏览器直传，再由后端核验并登记。最终被业务引用的对象使用独立且不可被原上传授权覆盖的 key，上传确认可通过服务端复制或写入最终对象实现；长期凭证不交给浏览器，未完成的上传不形成业务引用。

OSS Bucket 与对象保持私有。文章图片通过带文章上下文的媒体接口访问，Rust 检查发布状态、文章与文件关联及文件可用状态后流式返回；管理者登录后才可预览草稿图片。图片路由使用 no-store，Caddy 及后续 CDN 不缓存；HEAD、条件请求与 Range 请求同样先鉴权，访客不获得绕过文章状态检查的 OSS 下载直链。

撤回事务提交后才开始权限校验的公开图片请求被拒绝；已授权的在途传输可完成，已下载内容无法收回。共享图片按文章访问入口控制，其他仍公开文章的合法入口继续可用。图片读取会消耗 VPS 带宽，第二阶段部署前验证资源预算。

Logo、头像、浏览器图标、默认分享图和友链图标通过各自的站点媒体入口读取。该入口仅允许当前公开站点配置或可见友链实际引用的系统文件，由 Rust 校验关联后返回，不能作为任意文件 ID 的通用公开下载入口；未公开或已移除的引用不开放读取。同一对象具有其他合法公开引用时，只能经对应入口访问，文章撤回仍使该文章的入口失效。

### 部署与发布

Caddy 入口服务独立为一个 Portainer Stack，应用使用另一套 Stack；Portainer 自身由服务器 Compose 启动和恢复。Caddy 配置及证书状态持久化，配置保存在面板之外，证书等持久化状态另行备份到服务器外；保留 SSH 和通过回环地址端口建立 SSH 隧道访问 Portainer 的恢复路径。

应用 Stack 包含 Rust API、PostgreSQL、管理端静态服务和必要备份任务，第二阶段加入 Nuxt。管理端静态产物打包为独立静态服务镜像，由其中的 Caddy 承载，与 Rust API 分别构建和部署；入口 Caddy 负责反向代理，以保持入口 Stack 独立发布。入口和应用通过受控共享网络连接，数据库仅在内部网络可达。

GitHub Actions 安装锁定的 mise 与项目工具，调用与本地相同的 mise 任务执行格式、静态检查、测试、契约生成验证和镜像构建，结果推送 GHCR。容器构建阶段复用相同版本与任务定义，运行阶段仅保留服务实际需要的依赖。发布记录关联提交、版本和镜像 digest；管理者通过 Portainer 手动选择版本，生产 VPS 运行已构建镜像。数据库迁移作为明确的升级步骤执行，并说明与旧镜像的兼容范围；镜像切换不等于数据自动回滚。

日志使用结构化输出和请求标识，配置日志轮转、健康检查与优雅退出。Session、密码、访问凭据和签名 URL 不进入普通日志；具体资源限制、连接池和密码哈希并发通过目标配置测试确定。

### 备份与恢复

已确认目标针对服务器故障、外部备份和 OSS 文件仍可用的恢复场景：RPO 不超过 1 小时，RTO 不超过 24 小时。保留最近 24 小时的密集恢复点，再保留更早每日一份，覆盖 30 天历史窗口；清理依据快照时间，至少保留一份跨越最近 24 小时边界的有效恢复点，避免分层保留产生间隙。

首版小型数据库优先采用每 30 分钟一次的一致性 pg_dump 自定义格式归档，完成后加密上传独立私有 OSS 备份 Bucket，并校验完整性。以成功保存到服务器外的有效备份快照时间计算年龄，可保守使用任务开始时间；调度、导出、加密、上传和校验总延迟必须留出重试余量，不能用上传完成时间替代快照时间。

备份失败及时重试，并在接近或超过恢复窗口时报告异常；告警渠道在上线前配置。定期在隔离环境真实解密、还原数据库和检查关键数据及关联文件，单纯存在备份文件不作为可恢复证明。若全链路耗时、资源开销或恢复时间不达标，转而评估物理备份与 WAL 归档。

上传核验并完成最终对象写入后才提交数据库引用；删除先撤销当前有效引用，物理清理延后，并保护仍被保留备份引用的文件。保留期限按不再被使用的时间计算，覆盖 30 天历史窗口和恢复缓冲，而非按对象创建时间直接删除；若依赖历史版本还原，数据库保存对应 versionId。

数据库角色、部署配置、Caddy 证书及持久化状态、恢复凭据和解密材料均有服务器外的恢复途径。恢复演练覆盖新服务器重建、入口状态恢复、数据库还原、关联文件可用性和服务重新开放；还原后的 Session 清空，管理者重新登录，并在开放公开访问前核对恢复出的发布状态。每次演练记录恢复点与实际耗时。

| 第一阶段上线 | GHCR 镜像、Portainer 发布、Caddy、备份与恢复入口 | 目标机器运行验证和恢复演练达到已确认目标 |

## 测试决策

验收以外部可观察行为为主，优先选择 HTTP 接口与真实 PostgreSQL 的边界，少量浏览器流程串联关键用户操作。仓库目前没有应用代码或既有测试体系，因此建立这一组共同边界，避免每个业务模块各自设计内部测试框架。

| 边界 | 验收重点 |
|---|---|
| API 与真实数据库 | 鉴权、Session、CSRF、数据库约束、事务、任务历史、习惯与日期、每日记录唯一性、导出、版本冲突 |
| 浏览器关键流程 | 登录、创建与完成任务、Markdown 编辑预览、补记、每日记录和回顾；第二阶段发布与撤回 |
| 契约与构建 | OpenAPI 3.1 产物、字符串 ID、可空字段、枚举与日期、生成差异、类型检查、空库及升级迁移、镜像可追溯 |
| 工具环境与质量 | mise 锁定版本可重建；rustfmt、Clippy、ESLint、Prettier 和 Vue 类型检查实际覆盖源码；检查不修复源码，错误与 lint 警告使本地和 CI 失败 |
| 第二阶段公开边界 | SSR HTML、列表、详情和媒体可见性一致；缓存、HEAD、Range 与条件请求不会绕过撤回权限 |
| 真实环境 | 实际 OSS 兼容、GHCR 拉取、Portainer 更新、恢复入口、目标机器资源和完整备份恢复演练 |

单元测试仅补充适合独立验证的复杂日期计算、解析或校验规则；不测试依赖库自身行为，不逐个镜像实现细节。安全验收包括 Markdown 危险 HTML 和链接不执行脚本，以及私人数据不会进入公开响应或统计。

- 自动生产部署、云服务整体故障下的额外跨地域恢复承诺。
