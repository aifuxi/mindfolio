# 第一阶段上线与恢复规格

Status: ready-for-agent

## 问题陈述

第一阶段的私人业务与手动数据导出已经完成，但目前只有开发环境和检查流水线。管理者还不能在目标服务器上通过固定版本镜像发布应用，也没有服务器外的自动备份、故障恢复路径和经过演练的恢复时间。因此现有功能尚不能作为可靠的日常个人入口使用。

依据：[功能范围](../product-scope/spec.md)、[技术实施规格](../technical-plan/spec.md)、[验收边界](../technical-plan/testing-plan.md)、[部署调研](../technical-plan/deployment-research.md)、[部署 ADR](../../docs/adr/0005-caddy-portainer-deployment.md)、[存储 ADR](../../docs/adr/0009-external-object-storage.md)、[上一批规格](../personal-routine/spec.md)。

## 解决方案

为现有 Rust API 和 Vue 管理端构建可追溯的生产镜像，通过 GHCR 发布。将 Portainer、独立的入口 Caddy Stack 和应用 Stack 的配置及操作说明纳入仓库；管理者通过 Portainer 手动选择镜像版本。为 PostgreSQL 与入口恢复所需状态建立服务器外备份、失败告警和保留策略，随后在目标环境验证发布并在隔离环境完成恢复演练，达到已确认的 RPO 与 RTO 后开放第一阶段管理入口。

## 用户故事

1. 作为管理者，我希望每个可发布版本都对应明确的提交和镜像 digest，以便知道服务器实际运行的代码。
2. 作为管理者，我希望升级前能执行明确的数据库迁移步骤，并知道旧镜像的兼容范围，以便安全更新。
3. 作为管理者，我希望通过独立的入口 Stack 和应用 Stack 管理服务，以便应用发布不改动入口配置。
4. 作为管理者，我希望 Caddy 故障时仍能通过 SSH 与 Portainer 的回环端口恢复，以便保留管理入口。
5. 作为管理者，我希望管理端与 API 在同一 HTTPS 来源下工作，以便登录、Cookie 与 CSRF 行为符合已有约定。
6. 作为管理者，我希望 PostgreSQL 定期形成加密的服务器外备份，以便服务器故障时保留私人数据。
7. 作为管理者，我希望备份失败或有效恢复点过旧时收到异常报告，以便在恢复窗口失效前处理。
8. 作为管理者，我希望备份保留覆盖最近 24 小时的密集恢复点及更早的 30 天历史，以便选择合适的恢复时间。
9. 作为管理者，我希望能在隔离环境从服务器外备份恢复数据库和入口状态，以便证明备份可用。
10. 作为管理者，我希望恢复后重新登录并核对关键数据，以便确认个人入口可继续使用。
11. 作为管理者，我希望在目标服务器实测健康检查、资源占用、日志和手动更新，以便确认现有设备能承载第一阶段。

## 实施决策

- 延续现有 `mise` 统一入口、锁定工具链、`mise run ci`、Rust DTO 契约和私人认证边界。生产镜像只包含运行所需内容；管理端由独立静态服务镜像承载，API 与数据库仅通过受控网络连接。
- GitHub Actions 在现有检查通过后构建并发布 API 与管理端镜像至 GHCR。发布记录关联 Git 提交、版本标识和不可变镜像 digest；PR 检查不推送生产镜像。目标服务器只拉取镜像，不承担编译。
- Portainer 由服务器 Compose 启动，9443 仅绑定回环地址；入口 Caddy 和应用分别由独立 Stack 管理。入口与应用共享受控外部网络，PostgreSQL 仅在应用内部网络，数据库和 API 不直接暴露公网端口。
- 管理端和 `/api` 使用同一 HTTPS 来源，代理保留现有 `/api` 去前缀约定。`AUTH_ORIGIN` 为实际管理来源；域名权威 DNS 托管在阿里云，入口 Caddy 通过 AliDNS DNS challenge 申请证书。具体域名、镜像可见性、服务器架构、资源限制及告警渠道在目标环境接入前填写，不把秘密写入版本库。
- 迁移作为明确的升级步骤运行；记录当前数据库与旧镜像的兼容范围。镜像回退不等于数据库回滚。生产发布由管理者在 Portainer 手动选择版本。
- PostgreSQL 首版每 30 分钟生成一致性 `pg_dump` 自定义格式归档，加密后上传独立私有 OSS 备份 Bucket 并校验。有效恢复点年龄以快照时间计算，目标 RPO 不超过 1 小时；备份失败及时重试并在恢复窗口接近失效时报告异常。
- 备份保留最近 24 小时密集恢复点及更早每日一份，覆盖 30 天历史，并保留跨越最近 24 小时边界的有效恢复点。解密材料和恢复凭据独立于服务器保存。
- Caddy 配置、证书状态、Portainer 配置及数据库角色等恢复所需资料有服务器外途径。隔离恢复演练记录恢复点、关键数据核对和实际耗时，目标 RTO 不超过 24 小时。第一阶段尚无文章媒体，关联文件恢复在第二阶段扩展演练。
- 日志结构化且带请求标识；Session、密码、凭据、签名地址不进入普通日志。目标环境验证健康检查、优雅退出、日志轮转和资源占用。

## 测试决策

- 沿用现有最高验收边界：`mise run ci` 覆盖源码、契约、测试和构建；镜像任务补充容器启动、健康检查及管理端同源代理的外部行为验证，不逐项镜像 Dockerfile 实现。
- 在目标环境核对 GHCR digest 拉取、迁移、手动更新、HTTPS 来源、Cookie、CSRF、内部网络、资源限制和恢复入口。仅有本地 Compose 启动不能证明目标部署成功。
- 在实际备份 Bucket 验证加密上传、校验、保留、失败重试及告警；以服务器外快照时间计算 RPO。隔离环境实际解密并还原数据库与入口状态，核对关键私人数据和重新登录，以演练耗时计算 RTO。
- 每项任务验收后写回结果并单独提交；目标环境尚未具备时，不把模拟结果记录为真实验收通过。

## 范围之外

- 第二阶段的公开网站、文章、友链、媒体访问与访问统计。
- 自动生产发布、数据库自动回滚、跨地域整体云服务故障恢复承诺。
- 把手动 JSON 导出当作自动数据库备份，或在第一阶段提前开发文章文件存储。
